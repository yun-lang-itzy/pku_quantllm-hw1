# 量化交易系统架构

本页的通用设计仍为教学草稿；末尾 VeighNa 实例已对照固定源码核验。先研究数据、事件与账户的一致性，再扩展性能与复杂策略。

## 一次交易决策经过什么

```text
行情/参考数据 → 校验与存储 → 特征/策略 → 目标仓位
                                         ↓
成交/订单回报 ← 执行适配器 ← 订单前风控 ← 订单意图
      ↓
账户账本与持仓 → 绩效、风险监控与对账
      └────────→ 下一次决策使用的账户状态
```

策略提出目标，组合/订单生成模块比较目标与当前持仓、未完成订单后产生订单意图。风控检查通过后交给执行层。订单接受不等于成交；成交和费用进入账本，才改变实际持仓与现金。

## 模块边界

| 模块 | 输入与输出 | 关键问题 |
| --- | --- | --- |
| 数据层 | 原始行情 → 统一数据事件 | 当时可获得吗？缺失、复权、时区一致吗？ |
| 策略层 | 数据与可见状态 → 目标或信号 | 是否偷偷读取未来数据或真实执行层？ |
| 组合/订单层 | 目标、持仓、在途订单 → 订单意图 | 会不会重复下单或超额买入？ |
| 风控层 | 订单与账户状态 → 放行或拒绝 | 资金、仓位、行情时效与限制是否满足？ |
| 执行层 | 已批准订单 → 状态与成交事件 | 如何处理拒单、部分成交、超时和恢复？ |
| 账本与对账 | 成交/费用 → 现金、持仓、净值 | 重复事件会不会重复记账？与外部账户一致吗？ |
| 观测层 | 版本、事件、指标 → 诊断记录 | 能否重放并解释每一步变化？ |

## 回测和运行环境

可复用策略接口、事件定义、账本规则和部分风险约束。执行与数据接入应使用不同适配器：历史回放并不能证明实时执行会有同样的价格、延迟或成交率。

建议每次运行关联 `run_id`、数据版本、策略版本、参数、订单编号和事件时间，便于从异常净值追溯到具体成交。

## 自测问题

- 策略目标不变但上一笔订单仍在途时，是否会再下同一笔订单？
- 接到重复成交回报时，哪个模块负责去重，依据是什么？
- 历史回测与实时运行究竟共享了哪些业务规则？
